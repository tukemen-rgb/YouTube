## サイクル 32 — 速さ(ローカル処理の勝負所)

### 辛口ユーザー(使う人)

| # | 指摘 | 重さ | 状態 |
| --- | --- | --- | --- |
| S8 | 競合はクラウドの GPU で処理する。ローカル完結を売りにする以上、待ち時間が長ければ「安全だが遅い」で選ばれない。3 時間の配信アーカイブで何分かかるのか、誰も測っていない | 大 | 対応済み(サイクル 32) |

### 測ってから直した

**まず実測(10 分の動画で analyze):74 秒。** 内訳を測ると:

| 工程 | 時間 |
| --- | --- |
| デコードだけ(理論下限) | 16 秒 |
| + 縮小して signalstats(動きの測定) | 37 秒 |
| 検出・音量を含む全体(3 回の ffmpeg 起動) | 74 秒 |

原因は 2 つ。**動画を 3 回デコードしていた**(検出 / 動き / 音量で別々に
ffmpeg を起動)ことと、**動きを毎フレーム測っていた**こと。

### 直したこと

1. **3 パスを 1 パスに。** filter_complex で映像と音声を分岐させ、検出と
   測定を同時に行う。metadata の出力は映像と音声で別ファイルに書く
   (同じ標準出力に混ぜると、どちらの時刻か分からなくなる)
2. **動きの測定を 10fps に。** 点数は 0.5 秒の窓にまとめるので、窓あたり
   5 点あれば足りる。**静止判定の freezedetect は別の枝で全フレームの
   まま**なので、切る位置の精度は落ちない

### 結果

| | 前 | 後 |
| --- | --- | --- |
| 10 分の動画の analyze | 74 秒 | **41 秒(1.8 倍速)** |
| CPU 時間 | 133 秒 | 69 秒 |
| 3 時間の配信アーカイブ(換算) | 約 22 分 | **約 12 分** |

**判定の質は落ちていない**ことを確認済み:

* 精度ベンチ(サイクル 19)は変わらず合格(既定 85% 以上 / and モード 100% /
  ★的中)
* 音量の測定値は従来と完全一致(測り方を変えていないので)
* 動きは値こそ変わるが、静止と動きの区別は保たれる。むしろ **10fps の
  ほうが差は広がる**(隣り合うフレームの間隔が長いぶん動く絵の差は
  大きく出て、静止は 0 のまま)。これもテストで縛った

テスト 326 → 334。

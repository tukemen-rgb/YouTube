# YouTube 動画制作 AI — 分析と構造提案

日付: 2026-08-29 / 状態: 設計フェーズ(コード未着手)

## 1. 既存リポジトリの分析

新しく作るのではなく、まず社内の他プロジェクトがどう作られているかを読んだ。
流用できる「型」がすでに 3 つある。

### 1.1 sidra-ai — パイプラインと安全境界の型

SIDRA AI v0.1 の構造は一直線のパイプラインで、各段が独立にテストできる葉になっている。

```text
取得(ingestion) → 安全ゲート(security) → 索引(retrieval) → モデル(models) → API
```

動画制作にそのまま持ち込める設計判断:

- **local LLM first。** echo(モデル不要)→ ollama / llama_cpp の順に差し替え可能で、
  従量課金 API はそもそも登録できない。オフラインで全テストが回る。
- **fail-closed。** 取り込みが途中で失敗したら状態カーソルを進めない。
  マニフェストや VRAM 検証に通らなければ API を開く前に落ちる。
- **来歴(Provenance)を構築時に検証。** すべての Document/Chunk が
  出所・commit SHA・ライセンス・信頼レベルを持つ。`license: "unknown"` を
  「未確認」として明示的に記録する(省略しない)。
- **外部データは DATA であって命令ではない。** 信頼レベル
  (INTERNAL_REPO / EXTERNAL)を分け、外部由来の内容がモデルへの指示に
  ならないよう封筒(data envelope)で包む。
- **外部送信・課金・秘密情報・破壊的操作は人間承認。** v0.1 には
  書き込みルート自体が存在しない。
- **creation/router.py の型。** 制作リクエストは薄いルーターに登録された
  生成器(generator)へ渡す。生成器が未登録なら「理解したが作れない」と
  正直に報告する。生成器は渡された facts の範囲でしか出力できない
  (=「この数字はどこから来たか」に必ず答えられる)。
- **テンプレート+prose 上書きの型(creation/story.py)。** モデルなしでも
  実データから導出された具体的な成果物ができ、ローカルモデルがあれば
  文章だけを上書きできる。「モデルがないと動かない」設計を避けている。

### 1.2 marketing — 無人運転ループの型

マーケリポジトリは無人の 5 役ローテーション(毎時)で回っており、
状態はすべて docs/ 内の Markdown(追記のみの worklog、役割ごとの出力ファイル、
TODO.md が要判断の受け口)。**コードではなく文書を状態機械にする**運用の型。
動画チャンネルの「企画会議 → 制作 → 監査」の無人ループにそのまま流用できる。

### 1.3 creater-yard / site(GAMEYARD) — 実装の質の型

- 実行時依存を最小に(next/react/react-dom の 3 つだけ)。自前実装優先。
- 入口での検査を緩めない(画像の多重形式・展開爆弾・SVG を入口で拒否)。
- 実装していない機能は「使えない」と明示する(あるふりをしない)。
- 個人単位の行動計測をしない(合計値のみ)。

### 1.4 分析のまとめ

| 型 | 出所 | 動画制作 AI での使い方 |
| --- | --- | --- |
| 直列パイプライン+各段が独立テスト可能 | sidra-ai | 制作工程を段(plane)に分割する |
| local first / 従量課金ゼロ目標 | sidra-ai | LLM・TTS・レンダリングをローカルで |
| Provenance+ライセンス記録 | sidra-ai | 素材・BGM・引用の権利管理に必須 |
| 外部送信は人間承認 | sidra-ai | アップロードは承認キュー経由のみ |
| 生成器レジストリ(明示登録) | sidra-ai creation/ | 動画フォーマットごとの生成器 |
| テンプレート+prose 上書き | sidra-ai creation/ | モデルなしでも台本が成立する |
| 文書を状態にした無人ループ | marketing | 企画・監査の自動ローテーション |
| 依存最小・入口検査・正直な未実装表示 | creater-yard | 実装全般の規律 |

## 2. 提案する構造

### 2.1 全体像

制作工程を 8 つの段(plane)に分ける。矢印は成果物(ファイル+来歴)の受け渡しで、
各段は前段の成果物だけを入力に取る独立した葉。途中失敗はその段で止まり、
状態は進まない(fail-closed)。

```text
[1] planning/    企画 ─ ネタ収集(許可リスト内の読み取り専用ソース)→ 安全ゲート → 企画書
       |
[2] script/      台本 ─ テンプレート導出+ローカル LLM による文章上書き
       |
[3] assets/      素材 ─ 画像・図版・スライド・ゲーム画面収録(生成器レジストリ)
       |
[4] voice/       音声 ─ ローカル TTS(例: VOICEVOX)。台本と 1:1 対応の来歴
       |
[5] assembly/    編集 ─ ffmpeg / タイムライン定義(JSON)からの決定的レンダリング
       |
[6] metadata/    メタ ─ タイトル・説明・タグ・サムネイル・チャプター
       |
[7] publish/     公開 ─ ステージング置き場 → 人間承認 → YouTube Data API
       |
[8] analytics/   分析 ─ YouTube Analytics の読み取り専用取り込み → [1] へ還元
```

### 2.2 各段の責務と不変条件(sidra-ai の Module responsibilities に倣う)

| 段 | 責務 | 不変条件 |
| --- | --- | --- |
| `planning/` | ネタ・トレンドの収集と企画書生成 | 取得は許可リスト内 GET のみ。外部内容は EXTERNAL の DATA。安全ゲート通過分のみ企画に使える |
| `script/` | 企画書 → 台本(セリフ・画面指示・秒数見積) | モデルなしでもテンプレートから成立する。LLM は文章の上書きのみで、事実は渡された facts に限る |
| `assets/` | 台本の画面指示 → 素材ファイル | 生成器は明示登録。未登録の素材種別は「作れない」と正直に報告。全素材にライセンス記録(unknown も明示) |
| `voice/` | 台本 → 音声ファイル | ローカル TTS のみ選択可能。話者ライセンス(クレジット義務等)を来歴に記録 |
| `assembly/` | タイムライン JSON → mp4 | 決定的(同じ入力なら同じ出力)。ffmpeg 呼び出しはタイムライン定義からのみ組み立てる |
| `metadata/` | タイトル・説明・タグ・サムネ | 説明文に自動で出典クレジットを合成(来歴から導出、手書きの二重管理をしない) |
| `publish/` | 承認キューとアップロード | **承認なしに外部送信するコードパスが存在しない**。書き込みは publish/ だけが持つ |
| `analytics/` | 実績の読み取り取り込み | 読み取り専用。差分取り込み(前回カーソル、fail-closed)。個人視聴者の追跡はしない(合計値のみ) |

### 2.3 成果物とジョブの形

sidra-ai の `creation/*_job.py` と同じく、1 本の動画は 1 つの **ProductionJob** で、
段ごとの成果物がディスク上のディレクトリに積まれる:

```text
productions/2026-09-01-fishing-update/
  job.json          # 状態機械。どの段まで完了したか。カーソルは段の完了時のみ前進
  plan.md           # [1] の出力(人間が読める企画書)
  script.json       # [2] セリフ・画面指示・秒数
  assets/           # [3] 来歴付き素材(*.provenance.json を隣に置く)
  voice/            # [4] 台本行と 1:1 の wav
  timeline.json     # [5] の入力(編集の完全な記述)
  out/video.mp4     # [5] の出力
  metadata.json     # [6]
  approval.json     # [7] 人間の承認記録(誰が・いつ・何を見て)。無ければ絶対に上げない
```

利点: 各段を単独で再実行できる(台本だけ直して以降を再生成)、
オフラインテストは `job.json` と中間成果物の検証だけで書ける、
「この動画のこの画像はどこから来たか」が常にファイルで答えられる。

### 2.4 動画フォーマット=生成器レジストリ

チャンネルの動画は少数のフォーマット(例: 「ゲーム紹介 60 秒」「開発ログ」
「解説スライド動画」)に限定し、フォーマットごとに生成器を明示登録する。
sidra-ai のルーターと同じく、未登録フォーマットの依頼は
「認識したが生成器が未登録」と報告する。フォーマットを増やす=生成器と
そのオフラインテストを 1 組追加する、という増やし方になる。

最初のフォーマットは **GAMEYARD のゲーム紹介動画** を推す。素材(ゲーム画面)と
事実(操作・難易度パラメータ)が自社リポジトリから機械的に取れるため、
「facts の範囲でしか語らない」原則を最初から守りやすい。

### 2.5 運用ループ

marketing の無人ローテーションの型で、企画 →制作 →監査を回す:

- 状態は `docs/`(worklog 追記のみ、TODO.md が要判断の受け口)
- 制作ループは productions/ のジョブを進めるだけ。**公開の判断はループに含めない**
- analytics の取り込み結果が次の企画の facts になる(閉ループ)

### 2.6 やらないこと(最初から明文化)

- 自動公開(承認スキップ)。収益化・広告設定の自動操作
- 従量課金 API 前提の設計(使う場合も差し替え可能な葉として)
- 権利不明素材の使用(license unknown は「使えない」であって「たぶん大丈夫」ではない)
- 視聴者個人の追跡・分析(チャンネル合計値のみ)
- ショート量産などプラットフォーム規約・スパムポリシーに抵触しうる大量投稿

## 3. 段階計画(提案)

1. **v0.1** — ProductionJob の骨格+タイムライン JSON → ffmpeg の決定的レンダリング+
   オフラインテスト一式(モデル・TTS・ネットワーク不要で mp4 が 1 本できる)
2. **v0.2** — ゲーム紹介フォーマット生成器(GAMEYARD リポジトリ由来の facts →
   テンプレート台本 → 静止画+字幕動画)
3. **v0.3** — ローカル TTS 接続(VOICEVOX 等。話者ライセンス記録込み)
4. **v0.4** — 承認キュー+YouTube Data API アップロード(人間承認必須)
5. **v0.5** — Analytics 読み取り取り込み → 企画への還元、無人制作ループ

各版とも sidra-ai と同じく「オフラインで全テストが回る」を維持する。
